# Working on Continuum

Read README.md and CURRENT.md to orient, then follow the authoritative source for the fact you need. Explicit user requests for broader reading take precedence over this routine routing advice.

## Work coherently

- Preserve the mission and existing user authorization. Do not invent additional approval gates.
- Keep each change connected to an objective and a concrete completion condition.
- Record design decisions with evidence, alternatives, scope, and a condition that would reopen them.
- Distinguish implemented, built, tested under stated conditions, accepted, published, and activated. They are different facts.
- Keep source snapshots exact. Do not silently replace evidence or historical collaborator responses with a later summary.
- Use the protocol registry selectively. It discovers methods; it does not execute them or grant capabilities.
- Record known coverage gaps. A tree inventory or automated scan is not a full semantic review.
- Preserve one authoritative home per fact. A brief is a dated projection, not a second task database.

## Collaborating

Use isolated workspaces or explicit file ownership for concurrent changes. Keep objective, principal, worker, host, conversation, attempt, and operation identities distinct when available.

A sent handoff is offered. Received, accepted, completed, and effect-confirmed require the corresponding actual evidence. Do not claim that a repository can wake a dormant chat without a functioning host integration.

When using another model, preserve what it was actually given, actual returned model metadata, the visible response, and limits. Do not describe agreement as independent empirical confirmation.

## Core implementation

Use explicit versioned object encoding and established hashing libraries. Keep slow inference and testing outside short acceptance transactions. Reuse of an operation ID with changed request bytes must fail; an exact retry must recover the original result.

The local CLI currently trusts its caller. Acceptor strings are namespaces, not authenticated principals. Do not expose it as a multi-user network service until authentication, authorization, bounded input handling, and an explicit deployment model exist.

Add meaningful tests for changes to persistence, concurrency, identities, and failure recovery. Do not add tests that merely mirror prose or inflate activity. Run the checks relevant to the changed behavior.

## Publication

Original code, schemas, and project documentation are intended for MIT public release. Keep credentials, private source archives, provider secrets, unrelated user material, build outputs, and transient databases out of commits. Upstream protocols inform original adaptations; their private operational state does not become public project state.

Do not store raw hidden model reasoning. Use visible outputs, concise decision explanations, tool observations, and supported opaque continuation references under their actual access conditions.
