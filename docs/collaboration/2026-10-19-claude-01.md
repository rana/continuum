# Continuum: an independent design contribution

*Caveat: I have not read Base12, Prime Radiant, or any upstream source. Where I reference their lessons, I'm relying on your coordinator's summary. Treat everything below as design proposals for the source review to confirm or reject.*

## What Continuum fundamentally is

Continuum is a **ledger of accountable acceptance**. The question it answers is "what was accepted, by which authority, on what exact evidence, as seen through what context, by what executor?"

Artifacts are inputs to that ledger, not the point. "Repo" is the wrong word, but the bigger risk is identity drift. Continuum should not become a second home for facts that already have one. Source code should stay in git, and Continuum should reference commits by hash. Continuum owns the things nothing else owns: decisions, evidence applicability, receipts, and context projections.

## Five concrete choices

**1. Protocols are data records that current authority activates.**
- A protocol (Progress Brief, Holographic Walk) is a content-addressed manifest: purpose, inputs, required evidence kinds, stop and return conditions, and output shape.
- It becomes active only through an Acceptance by a named authority. Every run's receipt cites the protocol's hash.
- The "protocol list" is just a query over accepted manifests, not a separate registry.
- Skills and prompts fit the same shape. No plugin runtime yet.

**2. Executor provenance is declared, not trusted, and it never sets weight by itself.**
- Record an ExecutionContext: vendor, the model string as reported, requested versus reported settings (thinking mode or depth where exposed), tools available, context-pack hash, prompt hash, and timestamp.
- Mark every field as *declared* or *observed*.
- Reliability weight comes from evidence: independent checks passed, replication by a different executor, reviews survived. It does not come from model prestige.
- Re-evaluation is a new Proposal against the same inputs. Nothing is overwritten. "Undo" is a superseding Acceptance.

**3. Context packs are first-class, hashed artifacts with explicit omissions.**
- Each pack records the budget, what was included and why, and what was deliberately left out.
- Omissions are the interface losses the Holographic Walk summary warns about. Making them explicit is what turns a context pack into evidence rather than a convenience.
- Replay then gets two clean modes: same pack with a new executor, or a fresh projection.

**4. Releases are checkpoints in a continuous acceptance stream.**
- Acceptances flow continuously. A release is a named Snapshot root plus three things: the accepted claims it relies on, a known-gaps statement, and a declared audience with a compatibility promise.
- "Publish" means widening the scope of visibility of an acceptance beyond its acceptor. It is not a separate artifact type.

**5. Capacity is observed, attached to receipts, and never planned (yet).**
- Record measured wall time, memory peaks, failures, and host identity on each receipt.
- No scheduler, no capacity model, no resource ontology. Once receipts accumulate, scheduling becomes an evidence-backed later decision instead of speculation.

## Challenges

**Flawed premise: "a frontier model deserves more respect."**
That is an untested prior. Encoding it as weight bakes in exactly the bias that re-evaluation exists to correct.

**Flawed premise: "redo work when a new model ships."**
Mass replay is expensive and mostly wasteful. Replay should be *targeted*, using a query like: "accepted decisions whose load-bearing evidence came only from executors matching X, with no independent check."

**Scope creep to defer:**
- multi-vendor plugins
- Ollama or OpenRouter routing
- Bedrock and other API integrations
- Linux primitives beyond the basics
- assembly
- a model-debate harness

**Multi-model collaboration**, which you have found genuinely valuable, needs no special machinery. It is independent Proposals plus cross-review Evidence. The core already represents it.

**Merkle trees:** a genuine service for snapshot diffing and inclusion proofs over exact bytes. Not a reason to Merkle-ize everything. Defer transparency logs.

## The surprising high-value possibility: stale-context alarms

Because every Acceptance cites the context pack it was made under, *including its omissions*, Continuum can detect a specific situation automatically. When a newly accepted fact touches something that a past decision omitted or never saw, flag that decision for review.

This is something git cannot do. It is reverse dependency analysis over *what the decider knew*, not just over what the code imports. It also makes re-evaluation demand-driven rather than calendar-driven.

## On the small native core

Rust plus SQLite plus SHA-256, with Blob, Snapshot, untrusted EvidenceRecord, expected-head CAS, and atomic retries, is the right size. My recommendations:

**Keep the trust-critical path tiny:**
- verify hash
- CAS-append an Acceptance
- write the receipt atomically with the effect

**Resist new core tables.** ExecutionContext, protocol manifests, and context packs should be schema-versioned typed records stored as Blobs and referenced by Evidence. The core's guarantees should not depend on them.

**Fix canonical encoding now.** JCS or deterministic CBOR, chosen before any hashes persist. Otherwise identical records will hash differently, and you won't be able to fix it later without a migration.

**Make retries idempotent with explicit keys**, scoped per (acceptor, target), so a retried Acceptance can never double-append.

**SQLite in WAL mode with a single writer** is fine until receipts prove otherwise. That is the same rule as capacity: measure first.
