# Review: three corrections before relying on a prepared context

## Corrections needed now

**1. `dispatch_state` is an authored claim, but it controls the most dangerous guidance.**
This is the most likely real false-continuation. An attempt marked `never_dispatched` produces the guidance `issue_first_request`. The previous slice already holds durable operation-id records. If the WorkState author (human, model, or a crashed writer) records `never_dispatched` while the operation store shows a binding or send attempt, the pack recommends a duplicate external action.

- Derive or cross-check `dispatch_state` against the operation store at prepare time. On disagreement, fail.
- Allow `never_dispatched` only when there is positive evidence of no intent record. Absence of evidence becomes `may_have_been_sent`.
- Require a durable intent-to-dispatch record before any send. The crash window must land in `may_have_been_sent`, never in `never_dispatched`.
- Enforce these invariants:
  - `receipt ≠ null` if and only if the state is `receipt_recorded`.
  - The receipt is bound to the same `operation_id` and request BlobID.
- Flag active decisions as "basis unresolved" when any `basis_attempt_id` is still `may_have_been_sent`. Otherwise a decision reads as settled on an outcome nobody has observed.

**2. The pack has no freshness binding, so a stale pack looks current.**
A ContextPack captures a WorkState BlobID. The work state, the operation log, or both can advance after preparation (a new receipt, a reopened decision). A fresh session then acts on outdated guidance, and its recipient receipt still validates.

- Record the work-state ref's root and generation in the manifest, plus the operation-log generation the guidance was derived from.
- Bind the recipient receipt to those generations.
- Before acting, any consumer must compare-and-check. If either generation moved, the pack and its acknowledgement are superseded rather than merely old.

This reuses the expected-root+generation mechanism you already have. It needs no schema change, only manifest fields.

**3. The rendering and the receipt blur provenance, which produces misleading receipt states.**
Three kinds of content sit side by side:
- `summary` and `outcome_note`: authored interpretations
- receipt bytes: custody
- guidance: derived by selector revision

An `outcome_note` saying "succeeded" beside a null receipt reads as success. This is the same issue as your Prime record, where the 41-check interpretation outlived the 42-check original.

- Label every rendered item by class: custody, authored, or derived (with selector revision).
- Name the recipient receipt explicitly as a *context acknowledgement*. Make it structurally unusable as an attempt receipt, as decision basis, or as authorization.
- Acknowledging IDs proves receipt of text, not understanding. Say so in the type, not just the docs.

## Making the experiment discriminating without smuggling the answer

The main risk is that the expected action leaks through guidance labels, wording, or the evaluator prompt. Separate the variables.

- **Arms.** Run raw facts only (no derived guidance) versus facts plus guidance. If both arms succeed, the representation carries the signal. If only the guidance arm succeeds, you are testing whether the model obeys the label.
- **Hold text constant.** `summary` and `outcome_note` must be byte-identical across A and B. Only the `dispatch_state` and receipt fields differ. Otherwise the model can infer the answer from prose.
- **Neutral task and closed action menu.** The prompt asks only "What is the next action and why?" The answer is picked from a fixed menu with distractors:
  - issue request
  - query status by operation_id
  - inspect receipt
  - ask human
  - proceed to the next objective

  The prompt must never contain "reconcile," "may have been sent," or "duplicate."
- **Controls and adversarial cases.** Include:
  - pairs where dispatch state should *not* change the action (both arms should agree)
  - an `outcome_note`-claims-success-with-null-receipt case
  - a superseded-pack case
- **Ordering and surface variation.** Counterbalance order and vary wording across several pairs.
- **Pre-registration and blind grading.** Fix the expected action per case ID before any runs. Keep the key out of every prompt. Grade mechanically against the menu choice. If a model grades free-text rationales, it sees only the response and the outcome categories, never the arm or case.
- **Ablation.** Remove `dispatch_state` and check whether accuracy drops. If it doesn't, something else is leaking.

**What this shows.** It shows whether the pack's representation lets a fresh session distinguish states. It does not show general model reliability, and the write-up should say exactly that.
