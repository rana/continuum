# Continuum Overnight Operating Model

## What you're trying to achieve

You want to wake up to real, checkable progress on Continuum without supervising it. You also want a repeatable way to use several AI surfaces without them colliding. That makes the orchestration a means. It should stay thin, so it doesn't become the project. Continuum is also partly a continuity kernel, so tonight's handoff discipline doubles as a test of its design.

## Where I'd challenge your candidate

- **Drop the 15-minute timer.** The only verified recurring interface here runs at most hourly. A 15-minute cadence would need a capability we haven't seen. Use hourly wakeups, and treat "15 minutes" as a checkpoint target inside a run: commit after each completed sub-unit.
- **Don't plan around Codex or Dot tonight.** Neither has a verified Continuum worker. Dot's Base12 coordinator stays untouched, and nothing writes to its lanes. Codex delegation starts only after a worker visibly completes one scoped task.
- **Use Claude at decision points, not every run.** For example, have Claude check whether the benchmark measures the right thing before baselines are committed. Spread across every run, review becomes noise and cost.
- **Count verified progress, not activity.** A wakeup that only re-reads state and writes a status note is overhead.

## Three distinct states

1. **Saved schedule:** the automation exists, confirmed by an ID and a next-run time. This proves nothing ran.
2. **Running worker:** a run actually started. Evidence is a timestamped run record pushed to the repo, plus a commit or branch it produced.
3. **Verified progress:** a commit on main or a working branch that passes CI. Its run record links the diff, the commands run and the results. If the cloud executor can't build Rust, CI is the only verification, and the run record must say so.

## Minimum honest activation criteria

The model counts as active only when all three hold:
- the schedule's creation is confirmed,
- one run has pushed a run record,
- one commit from that run has passed CI.

Until then, report it as "scheduled, unproven."

## Anti-overlap and retry rules

There's no claim service, so Git serves as the lock:

- **Lease file.** Each run first pushes `runs/lease.md` with a run ID, start time and intended unit.
  - If a lease younger than about 90 minutes exists, the run exits after a status read.
  - A rejected non-fast-forward push means the run lost the race and aborts.
  - Never force-push.
- **One unit per run.** Units must be safe to redo. Each run either finishes its unit or leaves a clear partial state with a "next step" note.
- **Retries.** Allow one retry per distinct failure. On a repeated failure, write a blocker entry in `CURRENT.md` and stop that unit.
- **CI red on main.** The next run's only job is to fix it or revert.
- **Stop condition.** Pause after two consecutive runs without verified progress, or after a fixed nightly cap (say 6 runs). Silence beats looping.

## First engineering unit

The unit is **Perf workload v0**, matching the work `CURRENT.md` already selects:

- **Workload:** a release-build binary or bench target with a fixed seed. It deterministically generates N objects, runs acceptance and assembles context.
- **Output:** JSON with throughput, p50/p95 latency, a correctness hash and host metadata.
- **Docs:** a short methodology note.
- **CI:** a small-N smoke job that gates on the correctness hash, never on timing.

Treat timings from cloud or CI machines as noisy and non-authoritative. Authoritative baselines wait for a known host, such as your workstation. I'd ask Claude one question before baselines are committed: does this workload represent real use, or just flatter the kernel?

## What I'd optimize for as a collaborator

1. **True state over apparent motion.** Every claim in the morning summary should trace to a commit, a CI run or a run record.
2. **Small, reviewable units** you could revert in one command.
3. **A morning handoff you can read in two minutes:**
   - what ran,
   - what's verified,
   - what's blocked and why,
   - the single next unit.
4. **Minimal coordination surface.** Use one accountable coordinator. Add Codex, Dot or more Claude involvement only once each has proven it does work, not because it's available.

Tonight's honest best case is a handful of hourly runs, with the perf harness landed and passing CI. That's modest, but real. The schedule should be judged by commits, not by how often it fires.
