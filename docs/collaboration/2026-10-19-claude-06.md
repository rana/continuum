# Base12 Pattern for Overnight Continuity: Advice

**Short answer: yes for continuity, no for continuous execution.** The user's real need is to resume reliably without losing reasoning between Chat, Codex and sessions. Base12 already provides this: Chat holds research and architecture, Codex implements, and GitHub holds durable state. It does this without a new orchestration layer, and building one would add failure modes for no gain.

## Consequential correction

Base12 shows continuity, not autonomy. No Dot or Codex dispatch integration was found. The scheduled job can therefore only reconcile and reason over what already exists. Overnight implementation progress happens only if Codex tasks are queued before sleep. Claims that overnight progress is "continuous" should say this explicitly.

Two related limits:

- The job's model cannot be set to Sol, so its outputs should be treated as coordination, not authoritative engineering judgment.
- Hourly wakeups replace the 15-minute idea. That is fine because the work is gated by units of work, not by the clock.

## Minimal Research Delta

Commit one per unit in the repository, not only in the PR body. It should contain:

1. **Unit ID**, branch/PR and base commit SHA.
2. **Question addressed.**
3. **What changed**, in one or two lines.
4. **What we learned**: each claim paired with its evidence (exact command, CI run link, raw-data path).
5. **Negative findings**, including approaches that failed.
6. **Limits**: environment scope (e.g., cloud host unknown or noisy) and anything untested.
7. **Uncertain effects**, flagged and not retried.
8. **Unresolved question.**
9. **Next action**, with an owner (Codex, Chat or the user).

Anything beyond this belongs in REPORT.md or CURRENT.

## When to involve me versus Sol/Codex

Sol/Codex should do implementation, tests and the benchmark harness.

Bring me in at decision points rather than on every unit:

- reviewing the benchmark methodology before you trust the numbers;
- adversarially reading Research Deltas for overclaims;
- architecture forks;
- reassessment after two unproductive units.

I have no memory between requests, so paste CURRENT plus the relevant deltas each time.

## Criterion for genuinely working

The test is a morning check: starting from CURRENT alone, can you verify each overnight unit's claim from its linked evidence in about 10 minutes, and did each unit's evidence actually change or confirm the next action?

Signs it is not working:

- activity without evidence-backed movement, such as reconciling notes, restating plans or opening PRs that change no conclusion;
- the same next action repeating across units.

Either sign calls for reassessment, not more wakeups.
