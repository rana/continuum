# First Real-Use Trial for Continuum: Design Recommendation

**Status:** These are recommendations only. Nothing below has been deployed. Workstation installation, Codex dispatch and the hourly continuation have not been verified.

## What you're reaching for

You want a **practice ground**. Continuum should become a tool you think *with*, so that using it shows what it should become. Underneath that is a question no defect test can answer: *does this actually make continuation easier, or does it add paperwork?* You also want room to experiment without endangering Base12 or Prime Radiant.

## Where it runs

- **Now:** run it in the Chat executor, with GitHub as the durable exchange point. This already works.
- **Later, on the workstation:** admit it only after three things exist:
  - a pinned release binary,
  - a project data directory kept separate from that binary,
  - a backup step that runs before every upgrade.

  Installing from a moving source checkout is not acceptable.

## Consumers

1. **First: Continuum itself.**
   - It's public, already has handoffs, and every Chat↔Codex transition becomes a real test.
   - Risk: self-reference can hide awkwardness, because we already know the tool.
2. **Second: a small, independent, public CLI project in a sandbox** (e.g., a unit or date normalizer).
   - Its owner and vocabulary differ from Continuum's, which exposes assumptions that only fit Continuum.
3. **Base12 / Prime Radiant: deferred.**
   - Bring them in only after the trial, with their owners' consent, and with private sources staying private.

## Updating without losing evidence

- **Version stamping:** stamp each binary with its commit, build hash and supported store schema. Every receipt records the engine version that wrote it.
- **No silent migration:** a binary refuses to open a store with an unknown schema. A schema change means exporting to a new store alongside the old one, never altering it in place.
- **Backup before upgrade:** before swapping binaries, copy the SQLite file with a checksum into an archive.
- **Rollback:** restore the previous binary and its matching store file together.
- **Old binaries kept:** retain previous release binaries so historical verification can be rerun exactly.

## Bounded trial

**Scope:** about 10 real handoffs or two weeks, whichever comes first.

**Per handoff, record one short note in `trials/` on GitHub:**
- What the receiver needed but the pack lacked.
- What the pack included that went unused.
- Questions the receiver asked that the pack should have answered.
- Minutes spent on Continuum upkeep versus actual work.
- Whether anything was trusted only because the CLI trusts the caller.

**Beyond defects, watch for:**
- Workarounds.
- Steps people skip.
- Places where WorkState's shape feels forced.
- Whether whole-record byte-bounded selection is the right unit.

**Decision rule at the end:**
- If packs are routinely supplemented by hand, or upkeep regularly rivals work time, change the design before adding anything new.
- If neither happens, keep the current design and add the second consumer.

## Concept that use may reveal

**Gap records.** Today, dispatch states are claims written by the sender. The receiver could instead record a small "needed X, didn't have it" entry linked to the pack it received. Gap records would:
- turn context selection from a fixed rule into something that learns from observed use,
- begin to separate *observed* outcomes from *authored* ones.

Test this manually in the trial notes first. Only build it into the engine if the notes show a pattern.

## Next Codex unit (small, no new platform)

1. Version stamping, plus a check that refuses unknown store schemas.
2. A backup-before-upgrade script and a rollback procedure.
3. A `trials/` note template and README.
4. Optionally, ingest trial notes as EvidenceRecords. This should require no new engine semantics.
