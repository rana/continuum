# Continuum storage: should SQLite be replaced?

## Decisive requirements

Speed is not the main question. These properties decide the choice:

1. **One atomic acceptance step.** Binding the request identity, checking the head, generation and candidate, updating the head, and inserting the receipt must succeed or fail together.
2. **Durable acknowledgement.** A receipt must not be reported until it survives power loss. The current setting is WAL with FULL sync.
3. **Exact-retry semantics.** The historical result must be recoverable after the head moves, and a changed request reusing an operation ID must be rejected.
4. **Safe sharing across independent CLI processes**, with bounded waiting (currently a 5-second busy timeout).
5. **Engine-enforced invariants.** STRICT tables, CHECK, foreign keys, and triggers that make tables immutable.
6. **Recovery and inspection.** Crash recovery, online backup, and the ability to inspect the database with independent tools.
7. **Format stability and build footprint.**

## Strongest case for changing

- **Turso** is a real Rust implementation of SQLite-style SQL, not a wrapper. It could keep the schema-as-contract approach while dropping the C engine. It also offers MVCC and `BEGIN CONCURRENT`.
- **redb** is a different kind of thing: a Rust key-value store with no SQL. Its typed tables and copy-on-write ACID design are simple, and its file format is stable.
- Removing C would simplify cross-compilation and give one memory-safety story.

## Strongest case for keeping SQLite

- SQLite's process sharing, durability and recovery are mature, and the current tests already exercise them, including two process-crash cases.
- The invariants live declaratively in the schema, not in scattered Rust code.

## Is removing the C engine valuable in itself?

Mostly not.

- redb on Linux still uses libc locks, so a Rust engine does not mean no C ABI.
- SQLite's C is arguably among the most heavily tested code available.
- Removal becomes valuable only for a concrete reason: a target without a C toolchain, WASM, an audit or policy requirement, or measured build cost. None of these is evidenced yet.

## Storage ownership is the real fork

- **Fjall** prohibits opening the database from more than one process.
- **redb's** multiprocess support is experimental.
- **Turso's** multiprocess `.tshm` is experimental.

Adopting any of them, as things stand, means changing the architecture as well as the engine. Continuum would need either a single owning daemon (with lifecycle, IPC and upgrade concerns) or fail-fast exclusive locking that serializes all CLI use. That is a product decision, not a storage swap, and it should not happen during the handoff pilot.

## Overlooked integration and semantic risks

**Invariants silently move into application code.** With a key-value store, FK checks, CHECK constraints, immutability triggers and conflict-update behaviour become Rust logic. Every current and future write path must re-enforce them. The existing tests largely observe outcomes rather than prove that no bypass path exists.

**Default durability differs.** Fjall's default write reaches OS buffers, not stable disk. Using it without an explicit `SyncAll` per acceptance would break the retry guarantee: a receipt could be reported and then lost.

**Turso's partial compatibility carries its own risks.**
- Its documentation lists the features we use, but compound primary keys combined with triggers have not been run.
- File compatibility is only partial, so opening the same file with the `sqlite3` tool is unsafe.
- `sqlite3_backup` is stubbed, which leaves `VACUUM INTO` as the backup path.

**One issue is independent of the engine.** `Store::open` takes `BEGIN IMMEDIATE` even for read commands. Every read briefly holds the writer lock, so concurrent reads contend with acceptances. Switching engines will not fix this, and it may matter more than engine choice.

## Smallest informative next comparison

This should not be a benchmark or a migration. Proceed in this order:

1. **Engine-neutral acceptance contract (no execution).** Write the invariants and failure semantics above as a short document. Map each one to the current enforcement point: schema, transaction, or code. This fits the existing R&D and documentation authorization.
2. **Paper feature matrix.** Rate SQLite, Turso, redb and Fjall against that contract as "documented", "unexecuted", "absent" or "requires architectural change". Do not claim anything about speed.
3. **Turso conformance spike, only if separately authorized.** Run the existing DDL and acceptance transaction against Turso, with two concurrent processes and a kill partway through. This is the cheapest decisive test, because it reuses the schema unchanged.
4. **Fix `Store::open` under SQLite in parallel.** Use a read-only path or deferred transactions for reads, and measure the contention before and after.

## Recommendation

**Keep bundled SQLite through the real-use pilot.** Then:

- **If** a concrete reason to drop C appears, evaluate Turso first using the conformance spike above. Adopt it only once compound primary keys, triggers, `BEGIN IMMEDIATE`, busy handling, crash recovery and the `VACUUM INTO` backup path pass under multiple processes.
- **If** Continuum deliberately moves to a single owning service process, redb becomes a credible candidate, with invariants reimplemented and tested in Rust. Fjall is only viable with `SyncAll` on every acceptance.
- **Otherwise**, there is no evidenced reason to change.
