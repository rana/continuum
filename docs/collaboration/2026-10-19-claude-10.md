# Repairs, Fault Model, and First Experiment

## Corrections to my previous answer

1. **Custody.** A hash names bytes; it does not keep custody of them. Custody needs two things. Each consumer re-verifies the bytes against the recorded hash at read time. The record also binds which object a given outcome consumed. Hashing before commit only guarantees that the name matches the bytes at that moment.
2. **Sequence.** The global event sequence is an explicit field. It is allocated only when a new acceptance outcome is written, whether accepted or stale. Object-insertion records allocate none, and exact retries allocate none. The sequence is neither a byte offset nor a record ordinal.
3. **Single writer.** One writer does not remove coordination. It concentrates coordination in one lock or process, which still serializes the order and still needs a takeover protocol when that writer dies.
4. **Mapped segments.** Memory-mapping needs a lifecycle contract:
   - seal, sync, then publish through a manifest that is itself synced;
   - readers pin a published boundary;
   - compaction and garbage collection may not unmap or delete pinned segments.

   A "current" read means "as of a published boundary," not a lock-free view of the latest state.
5. **Prefixes.** Replaying write prefixes is not a fault model. Corrected model:
   - Blocks written but not yet synced may persist as any subset, in any order, each possibly torn at sector granularity.
   - Data acknowledged before a sync barrier is assumed to survive.
   - A torn, unsynced tail is classified as *tail*: it is discarded and was never acknowledged.
   - Damage inside acknowledged history is *corruption*: fail closed and never auto-truncate.
   - Directory and manifest updates are separate barrier events.
6. **Unvalidated claims.** I have not measured fsync dominance. Opening SQLite with deferred read transactions and moving hashing out of the write transaction are hypotheses to measure against the retained baseline, not required fixes.
7. **Trust.** Owned emission removes the external compiler and runtime from a *specified* trusted part. Kernel, filesystem, device, firmware, and the disclosed bootstrap seed remain trusted.
8. **Dependencies.** Use vetted, pinned, audited implementations of the integrity hash. Homemade cryptography is a liability. Checksums detect damage; they do not repair or authenticate.

## Choice: simulation first

I would start with a pure state machine plus a framed-record simulation. Two reasons:

- **The fault model can be enumerated in simulation and only sampled on real hardware.** A file journal tested first would mix bugs in our classifier with page-cache and filesystem behavior we cannot enumerate.
- **The record format and recovery classifier are the actual design object.** Simulation tests them against the existing reviewer proposal: object-insertion records, complete outcome records, rebuilt indexes, and today's identities, receipts, and sequence.

The real file journal comes second, with injected crashes and real-device spot checks. Those spot checks are explicitly *not* a power-loss proof.

## Acceptance criterion (bounded)

**Bounds.**
- Up to 2 heads, 3 operation IDs, 3 objects, and at most 6 requests.
- Request kinds: new, exact retry, changed-same-ID, stale precondition.
- All orderings within those bounds.
- Record frames: length, domain/version, type, payload, integrity hash, commit marker.

**Fault injections.** For every reachable history, inject:
- a crash at every write and barrier step;
- every subset and reordering of unsynced blocks;
- a torn cut at every sector of the last two records;
- a single bit flip at every byte of the last two committed records.

**Pass requires all of the following:**
- Every acknowledged outcome rebuilds byte-identically, including receipt and sequence.
- No outcome appears that was never acknowledged.
- Every recovered state classifies as exactly one of: clean, torn-tail, or corrupt-acknowledged. The last always fails closed. Zero states go unclassified.
- Results agree differentially with an oracle model of current SQLite semantics on the same request sequences.

This covers only these bounds. It says nothing about longer histories or physical power loss.

## What excites me most

The SQLite-versus-redb framing asked *which engine holds our state*. It never asked *what the recoverable states of our history are*. I most want to learn whether the complete acceptance-outcome record can be the sole unit of truth. If so, every index becomes a total, deterministic rebuild function, and recovery reduces to a three-way classifier we can enumerate.

If that holds, the storage engine becomes interchangeable: SQLite is one possible implementation of the classifier's contract. If it fails, we learn exactly which invariant needs a database.

A close second: whether the bounded model shows that the global sequence carries meaning no per-head generation provides.
