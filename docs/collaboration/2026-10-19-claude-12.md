# Conditional successor architecture: new repo versus refreshed current repo

**Status:** Nothing has switched. Rust/SQLite remains the working baseline, and the owned-native stack is unbuilt and unmeasured. Everything below applies only *if* owned-native is later adopted on evidence.

## Preferred fresh-reader information architecture

1. **README (front door):** what Continuum is, current contracts, implementation status, and the single next action.
2. **`CONTRACTS/`:** canonical object, acceptance, retry, and context semantics, stated independently of any stack. These carry over unchanged.
3. **`IMPLEMENTATION/`:** the owned-native design, including the state and recovery model, journal format, emitter, ABI, and bootstrap.
4. **`EVIDENCE/`:** baseline conformance results, counterexamples, and any comparative speed and reliability data that justified adoption.
5. **`PROVENANCE.md`:** a short page covering why the Rust predecessor was weighed and superseded. It links to a pinned predecessor commit or tag and does not retell the history.
6. **`BOUNDARIES.md`:** what is private, what is public, and what was not carried over.

## Criteria for a NEW repository

Create one only if most of these hold:
- The source tree shares little or no code with the Rust tree.
- The build toolchain or bootstrap is disjoint, so Cargo is no longer the build root.
- CI, release, and maintenance ownership differ materially.
- Keeping both trees in one place would force readers or tools to navigate two live build systems.

## Criteria for a REFRESHED current repository

Prefer refreshing in place if any of these hold:
- The owned components replace modules incrementally inside the existing build.
- The Rust implementation remains a conformance oracle that runs in CI.
- Issue, PR, and license continuity matter more than a clean tree.

Wanting a fresh narrative does not justify a new repo on its own. A rewritten README plus an archive tag can provide that.

## In either case

- Keep one write authority, with the predecessor marked read-only.
- Pin the exact baseline and counterexamples by commit hash.
- Write `PROVENANCE.md` only after adoption actually occurs, never in anticipation of it.

## Overlooked risk

A fresh repository can quietly sever the conformance oracle. If the Rust/SQLite baseline is archived rather than executed, the owned stack's correctness claims lose their reference implementation, and regressions in exact operation history become undetectable. Whichever option is chosen, keep the baseline runnable against the shared contract tests until the owned stack's own evidence stands independently.
