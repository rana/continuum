# Release-build workload baseline

`examples/measure_workloads.rs` measures existing native core operations in one process while checking their actual outcomes. It establishes a reproducible workload and a first observation under recorded conditions. It does not rank Rust against assembly, compare Continuum with Git or Scion, or establish production capacity.

## Run it

Use the normal locked dependencies. The example uses the existing `tempfile` development dependency and adds no dependency to the core.

```sh
cargo build --locked --release --example measure_workloads
target/release/examples/measure_workloads --samples 100 --directory /tmp > baseline.json
```

`--samples` defaults to 100 and accepts 1 through 10,000. `--directory` defaults to the operating system temporary directory. It must already exist. Each invocation creates its own temporary child directory and local SQLite database, then removes them. It never reuses or overwrites an existing database. Keep the JSON output outside that temporary child directory. A small correctness smoke run is:

```sh
target/release/examples/measure_workloads --samples 3 --directory /tmp > smoke.json
```

The program writes the JSON report only after every correctness assertion and database cleanup succeeds. An error or failed assertion exits unsuccessfully; any incomplete output must not be accepted as a result. Build and process startup costs are excluded from operation timing. A debug build can run the same correctness workload, but its `build.debug_assertions` field will normally be true and its measurements must not be labelled as the release baseline. The field records that compiler configuration, not an independently verified Cargo profile: retain the actual build command.

## Workload and checks

Each operation has the requested sample count. Inputs are generated deterministically without randomness, network calls or model inference. Every blob has a distinct 1,024-byte payload, and each source snapshot has one path. Every context contains six selected records: work identity, objective, one uncertain attempt, one active decision, one uncertainty and one offered handoff. It has an 8,192-byte budget, includes every record, and binds its exact work state to a distinct accepted target.

| Measured operation | Timed call | Correctness checked outside its interval |
|---|---|---|
| Insert a unique blob | `Store::put` | Returned ID matches the canonical object ID computed before timing. |
| Read an existing blob | `Store::get` | Recovered object equals the exact generated bytes. |
| Advance the current head | `Store::accept` | New accepted receipt, matching old head, expected next root and generation, and actual stored head. |
| Reject a stale precondition | `Store::accept` | New precondition-failed receipt and unchanged final head. Original requests' earlier preconditions are used with new operation IDs. |
| Retry an accepted request | `Store::accept` | Replayed flag and complete equality with the historical receipt; no added event or head movement. |
| Prepare a unique anchored context | `prepare_context` | Exact work-state reference, all six records included, no omissions, byte budget respected and matching anchor observation. |
| Prepare the same context again | `prepare_context` | Identical manifest, content ID and freshness observation. This is reported separately from first preparation. |
| Verify historical context | `verify_context` | Exact projection verification, matching bytes and context ID, current anchor observation, and no claimed action authority. |
| Verify current context | `verify_current_context` | The same checked projection plus its matching current anchor. |

Snapshot insertion, authored WorkState creation, and anchor acceptance are untimed setup. Those objects are small, fixed-shape fixtures, not a representative distribution of all future repositories. Uncertain dispatch is an authored fixture; the harness sends nothing externally. The existing scenario tests remain the home for crash recovery and stale-context rejection.

## Interpret timing precisely

The clock is `std::time::Instant`. Each interval surrounds one public API call and includes its result construction and the small timer overhead. Assertions, input construction and report formatting are outside those intervals, although they affect the overall run and the state of caches. No warm-up samples are discarded and no cache flushing occurs. Groups run in the reported order against one growing database: later operations see the objects and receipts written by earlier groups. In particular, reads and context verification use previously inserted data, and repeated preparation checks the existing-object path.

Raw nanosecond samples are retained in execution order. Minimum, maximum, p50 and p95 use the nearest-rank method: sort the observations and select index `ceil(p × n) - 1`. With three samples, p95 is the largest of those three observations. Even with 100 samples it is a descriptive statistic from one run, not a confident estimate of a stable tail latency. No significance test, confidence interval or overhead subtraction is performed.

`operations_per_timed_second` divides the number of calls by the sum of their individual measured intervals. It excludes setup and checking gaps and must not be presented as sustained end-to-end throughput. `workload_wall_ns_before_report_and_cleanup` includes the workload's setup and checks after argument parsing, but excludes process startup, JSON formatting/output, connection close and temporary-directory cleanup. Automatic SQLite checkpoints that occur within measured calls are included; shutdown checkpoint work is excluded with connection close.

`Store::open` requests WAL mode, FULL synchronization, a five-second busy timeout and foreign keys, with one connection in this harness. These are the core's configured settings, not a physical durability measurement. A database under `/tmp` might reside on tmpfs, an overlay filesystem, or another storage type. A result on any of these is an observation of that environment; it cannot be generalized to a workstation SSD or other storage without a corresponding measurement.

## Retain enough provenance to repeat the observation

Save the raw report with a run record containing:

- The exact source commit or tree, and any uncommitted harness/core changes. Include source file digests when the measured version has not been committed yet.
- The complete build and run commands, `rustc -Vv`, `cargo -V`, locked dependencies, and relevant build flags such as target CPU, LTO and custom profile settings. Do not capture an entire environment containing credentials.
- Operating system and kernel, CPU model and available CPUs, memory where available, actual filesystem/mount type for the selected directory, and whether this is a VM or container when known.
- Sample count, time of execution, competing load if observable, and any missing information. Do not describe unavailable host information as verified.
- Exit status, the raw result's digest, and the next question the result informs.

The report includes a digest over the deterministic blob fixtures and a semantic fingerprint over checked object IDs, acceptance receipts and context manifests. Repeating a run with the same source and sample count should preserve these fingerprints while timings change. They make fixture and outcome drift visible; they do not prove semantic correctness independently of the assertions and source review.

For comparisons, hold source, profile, fixture count, operation order and storage conditions fixed unless the experiment intentionally varies one of them. Start with several independent repetitions to see variation. Add a concurrency workload only when investigating a concrete contention question; this baseline has one worker and supplies no concurrent-throughput evidence. A small smoke run may be used as a correctness gate, but latency thresholds on shared CI should not be introduced without a controlled comparison method.

## Next question

After a recorded release run, identify which operation family and environmental factor warrants the next experiment. Plausible next questions include how write latency changes on a known local filesystem, how context cost changes with history size, or where contention begins with multiple independent workers. Choose from the measurements and project needs before changing the storage engine.
