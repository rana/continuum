## A source-derived gap between checked and parsed bytes

The [archive verifier](https://github.com/rana/base-12-ai/blob/88382e793b65c84fd8e223840c27f6bb8682864a/research/owned-stack/2026-10-15/decision-gate/verify_archive.py) first reads a path and checks the resulting byte array against fixed size, Git blob and SHA-256 identities. It then reopens the path for archive parsing. Later checks compare the parsed members to their parsed manifest, fixed member/entry counts and two separately fixed output digests.

A conditional adversarial schedule follows from that source, without executing it:

1. The first read obtains the expected archive A and passes its fixed identity checks.
2. Before the parser's second open, another actor replaces the path with archive B.
3. B preserves the expected root, counts and two fixed outputs, but changes another member and updates its own matching manifest entry.

Those later member/manifest comparisons do not bind B back to the raw bytes of A. The returned archive identity can therefore describe the first read while the member checks describe the second. This is **not an observed race, a reproduced exploit, a claim that the historical archive was replaced, or evidence that historical numerical checks failed**. If the input is genuinely stable through both opens, this schedule is excluded. The relevant limitation is that this verifier does not itself enforce that stability.

The transferable rule is small: parse the same retained bytes that were checked, or make and enforce the immutability assumption explicitly. Hashing a path twice at different stages is not a substitute for naming the exact byte object each stage consumed. The native backup's private staging and trusted-directory requirement address a related ownership boundary; they do not authenticate a hostile filesystem. This source review selects no Continuum code change and does not edit the private upstream verifier.
