## Research Delta: record intent, publication and batch outcome separately

Each worker syncs its initial journal row before its GET. That row records request intent; an interruption after the sync and before the call can leave it without a sent request. An attempt counter of one is not external confirmation. The helper has no per-file retry loop, and existing output/destination checks prevent an ordinary exact rerun from silently overwriting prior work.

After complete size/hash checks, it syncs the private partial file, acquires the publication/failure lock, links it into the data directory without overwrite, sets `published`, syncs that directory and removes the partial alias. Only then is the row marked complete. The final journal row and batch receipt follow. A post-link directory-sync, unlink or connection-close failure can therefore leave visible bytes and `published: true` alongside a failed status. This is a source-derived state, not an observed historical failure. Successful installation of one file is distinct from successful completion of the batch.

The initial row sync is useful ordering, but there is no atomic transaction covering installed files, both directory namespaces, journal rows and final receipt. A terminal journal failure can prevent the aggregate receipt; neither fresh-output creation nor the per-file no-overwrite link supplies a resume/reconciliation protocol. No crash, path replacement, filesystem fault or timeout was exercised here. Continuum should retain partial-effect states and inspect existing artifacts before retrying an uncertain operation.
