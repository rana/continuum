# Bounded owned CLI cost probe (declared before measurement)

Question: what does a fresh-process owned CLI operation cost as the bounded history grows, with the current version-2 fences/startup barriers enabled?

Source: `ea197d7c37352dbe13585ecf0e2c7fa489a03fe2`, storage implementation unchanged from `8bc0fc1578fb915f10fedd22ee016bf9c4e9b2df`. One original coordinator-authored probe; no upstream code or provider invocation. Disjoint from the separately owned design PR. Existing remote main, open PRs, repository instructions and unchanged design-owner activity were reconciled.

Protocol: build the existing owned-store CLI with Cargo's default release profile and locked dependencies. Three independently initialized disposable stores at each history size 1, 16, 64 accepted updates; each update adds a distinct 128-byte Blob, single-entry Snapshot and complete acceptance event. Measure eight full subprocess invocations per operation per store: get latest Blob, head, latest receipt, exact first acceptance retry, duplicate latest Blob put. Then measure one new stale acceptance. Verify full returned objects/heads/receipts and unchanged journal/boundary bytes for the non-appending operations. Independently decode each final journal and check semantic history against the existing Python oracle reader. Record individual wall times and stdout, not just aggregates.

Separately compile the existing Linux fsync interposer and run one instrumented sample of each operation per store with failure injection disabled. Check the expected successful sync calls (four for read/retry/duplicate, ten for new stale acceptance) and retain only role labels, never temporary absolute paths. Do not mix those instrumented times with the uninstrumented measurements. Measure serialized journal bytes and source payload bytes separately.

Completion: all semantic and byte-preservation checks pass; retained raw measurements bind exact source/binary identities and expose build/environment/workload/sample ordering. A failure is a failed probe, not silently discarded timing. No timing threshold, repeated-until-fast sampling, SQLite comparison, sustained-throughput, concurrency, cache-cold, physical-durability or deployment claim. Ascending history sizes and repeated reads introduce cache/order bias. Full CLI timings include process launch, output capture, recovery, synchronization and serialization; they do not isolate in-process lookup cost. Successful libc observations are not device acknowledgements. The one-MiB store and small synthetic workload limit extrapolation.
