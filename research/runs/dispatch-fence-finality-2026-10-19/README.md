# Dispatch fence finality: post-commit counterexample (2026-10-19 UTC)

## Research Delta

**Question and owner.** Can Continuum authorize a new external model request after a provider reports that all earlier submissions are *now* terminally fenced? This is a disjoint research result from the active Chat research session, not a Codex or Dot dispatch. Source orientation was public `main` at `4c21bd5a5e1b2634a4500bc1968e8a2f1f5ead70`; the publication was prepared on a newer observed `main` at `82354c23af60522be69207a29df787654965fb26`. The concurrent builder fixture/source-review lane and all implementation files are untouched. The prior [synthetic admission-race branch](https://github.com/rana/continuum/tree/research/2026-10-19-dispatch-admission-race) remains independent, with its historical uncommitted package retained in the originating conversation. This unit adds a *new* post-effect question rather than repeating those tests.

**Result.** A terminal fence that prevents **future** effects is *not* by itself evidence that no **prior** effect committed. A logically consistent trace is: old effect commits; acknowledgement is lost; fence rules out future old work; client treats fence as a retry grant; new epoch commits a second effect. An actionable fence must be both terminal and **outcome-bearing**: for the exact scope/key/request digest it must distinguish authoritative `none_committed` from `committed` or `unknown`, and cover all previous admitted attempts. Any downstream effect domain must be separately idempotent or conclusively reconciled. A response-validity check is independent of effect deduplication.

**Executed finite model.** `fence_oracle.py` enumerates 128 combinations and filters to 72 internally consistent synthetic worlds; a deliberately wrong `naive_retry` admits replay in 21 worlds where `conservative_retry` withholds it. Not all 21 imply an actual duplicate, because incomplete evidence can also justify holding; one explicit post-commit world yields two provider effects under the wrong rule versus one when held. The two functions are finite decision *models*, not provider-compatible code, proof of global exactly-once semantics, or a safe production runner. The fabricated `none_committed` report is presumed sound and atomic with the terminal fence. The simplified downstream boolean is only an adversarial reminder that provider-level dedup is not end-to-end.

**Verification.** In this run's Linux container on Python 3.13.5, `python3 -m unittest -v test_fence_oracle.py` exited 0 with seven tests, and `python3 fence_oracle.py` exited 0 with output `valid_synthetic_worlds=72 blind_fence_false_admissions=21`; the post-commit example produced `naive: (2, 0)` and `conservative: (1, 0)`. Prior separate admission-race source was recovered from the original attachment, its six recorded SHA-256 identities matched, and its eleven tests plus witness script also passed in the same executor. The older branch's tests and data are not silently represented as newly published code.

**Independent design challenge.** One *actual* supplied-context Claude Opus 5.5 review, configured `medium` effort/adaptive thinking, exposed the post-commit fence counterexample and clarified the downstream and response-availability boundaries. Exact supplied request, context, visible reply and returned metadata are in `claude-review.json`. This is a model critique, not empirical provider evidence. The local finite oracle was written and executed after the critique.

**Negative findings and limits.** No provider admission/finality API, retention policy, gateway fanout, real downstream side effect, verified authenticated receipt, physical power-loss durability or usable model response was exercised. A generic HTTP status, preflight positive binding, TTL, or cancellation acknowledgement is insufficient for external automatic retry. This result does not change Continuum's local Rust/SQLite acceptance semantics or claim a general external runner is active. The finite sweep is not an exhaustive model of networks, authentication, concurrency or time.

**Next action and actual owner.** The next available owner of the *external-dispatch research lane*, not the separate current builder review, should formalize a provider capability matrix with scope/key/digest binding, atomic admission linearization, terminal finality covering all earlier submissions, prior-effect outcome proof, downstream boundaries, and response retrieval semantics. Apply it to documented provider contracts and adversarial fake-provider schedules before implementing a runner. Until evidence of those primitives exists, retain `hold/reconcile` after an unknown external outcome. No future worker acceptance or migration is asserted.
