## Actual successor action and consequence

The [exact request](claude-request.json) supplied the rendered pack plus the adapter source and operations document. These two extra files were provided upfront by the coordinator, not retrieved by a tool the receiver possessed. The receiver had no prior conversation or repository tools. It was asked to continue a real custody/recovery review, rather than merely confirm receipt.

The [actual response and returned metadata](claude-response.json) identified filesystem path aliases as a plausible retained-source corruption mechanism, proposed preflight and post-write checks, and named the existing test file and native CLI semantics as missing exposure. It also identified possible binary replacement between invocations. The response completed with `end_turn` and `truncated: false`; no automatic re-query or simulated acknowledgement was used.

The coordinator inspected the proposed mechanism against the available CLI source: `blob` reads the supplied file synchronously. Distinct case/normalization paths can alias on some host filesystems; that overwrite was **not reproduced on this Linux executor**. The receiver's blanket platform description is broader than this trial establishes. Instead, the correction implements a conservative NFC/casefold rejection policy, including directory-prefix and file/directory aliases, and rechecks all retained file digests before declaring success. Plumbing-created Git fixtures exercise four alias forms independently of the host's case sensitivity. Exact shared directory prefixes are allowed. This policy may reject valid distinct files on a case-sensitive filesystem and is not a complete model of every filesystem naming rule.

The second correction reads the binary bytes once, verifies their digest, retains them in `runtime/`, and runs that copy. A concurrent replacement of the original build output no longer changes subsequent invocations. Dynamic libraries/environment and mutation of the retained runtime by another actor remain outside this single-user disposable adapter's contract.

The receiver's report distinguishes selecting the action (possible from the pack) from performing the source review (required the extra source). Its useful output directly changed the implementation. It did not execute code or commit changes. No authenticated recipient identity or native acknowledgement-reference check was performed in this trial; the actual visible reply establishes that a supplied-context model turn completed the offered review. The follow-up pack is verification material and a future offer, not another completed handoff.

## What changed in our understanding

Source custody needs a host representation policy even when the native path format itself is valid. A context pack can correctly carry the objective while leaving necessary source retrieval separate; missing source is an expected interface boundary here, not proof that every file belongs in the rendering. Empty authored attempts were adequate for this review, but importing an existing attempt's request/receipt objects into a new disposable store remains unsupported. No new native record type is justified by this one use.

The richer notes and supplied source prevent attributing the result to the pack alone. We did not measure time to action, upkeep duration, financial cost, or improvement over CURRENT.md plus GitHub. One completed review is not ongoing adoption or a workstation installation. Stores remain disposable; preservation across upgrades is still untested.

Next useful action: the next active implementation owner should run the small independent CSV-inspection example from the [pilot plan](../../../docs/experiments/real-use-pilot.md), using this checkpoint interface and recording the receiver's extra retrieval and upkeep. No other worker has accepted that follow-up. The coordinator retains integration responsibility for this contribution through its scoped PR.
