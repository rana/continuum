**Question.** Which conditions distinguish a safe external model/worker retry from a timed-out or apparently failed request that may still produce an effect? Continuum's SQLite accepted-head generation and exact historical retries **do not extend automatically to provider-side effects**. An external reply may be malformed/unaccepted even when an upstream transport status says HTTP 200, and a provider's point-in-time "not found" may precede a late original commit.

**Artifact and result.** The pure-Python model (`model.py`) enumerates 96 synthetic metadata combinations for one logical request; all pass its declared safety/availability checker. Six intentionally incorrect decision strategies have counterexamples, including blind replay after unknown outcome, replay after point-in-time absence, treating HTTP 200 as a valid model result, ignoring request identity, always holding even a definitely unsent request, and treating effect existence as usable output. Eight tests pass on Python 3.13.5 in a task-local Linux container. Rechecked in this publication run; see commands below. The original artifact's exact source was compared using Git blob identity when publishing; `result.json` retains the first synthetic report.

```sh
cd research/runs/uncertain-external-dispatch
python3 -m unittest -v test_model.py
python3 model.py
```

**Discriminating trace.** Send A may be in flight. A status query reports "not found" at time t. The caller sends B for the same logical operation. A then commits and B also commits. A point-in-time negative lookup is not a terminal no-effect certificate. If the original response is lost, "nothing usable returned" is likewise not "no effect." A receipt for an external effect may exist even when the response still requires independent validation/binding.

**Safe distinctions in the model.** A first send is allowed only with verified never-sent evidence. Exact replay is permitted with authenticated authoritative **final non-effect** or with an actually verified and still-valid provider idempotency guarantee for the exact request and operation identity. A pre-send rejection prompts a new corrected intent under a different operation identity; a known existing effect is reconciled rather than resent; uncertainty without those guarantees is held. A changed request under a reused operation identity is rejected.

**Limits and negative findings.** These are synthetic *assumed* finality, provenance, and idempotency capabilities, not observed provider guarantees or a claim of exactly-once external inference. The 96-case cross-product intentionally contains infeasible metadata combinations; it is not 96 independent real network traces. The checker and model were authored together, not externally proven correct. The model does not encompass multiple sends, malicious/contradictory attestations, asynchronous operation scopes, compound effects, idempotency expiry, or durable local intent writes. No native CLI, model service, external provider, remote executor or workstation was exercised. The earlier Claude critique attempt had no accepted response or usage metadata; its returned error and exact prompt are retained separately in `claude-attempt.json`; it was not replayed. No provider cause is inferred.
